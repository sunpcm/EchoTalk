# EchoTalk 架构演进规划

> 撰写：2026-11-11，基于 `claude/cloud-review-2026-11` 分支的代码阅读与
> [2026-11 云端评审](./reviews/2026-11-cloud-review.md)。
> 本文回答"接下来半年到一年，结构往哪里走、先后顺序是什么、每一步怎样算完成"。
> 它不是任务清单：可执行任务仍只写在 [TODO.md](../TODO.md)，现状见 [ARCHITECTURE.md](./ARCHITECTURE.md)。
> 文中的判断来自读代码和云端自动化，没有真实 LiveKit、Provider、IdP 或设备的证据；涉及这些的部分标为假设。

## 1. 一句话判断

EchoTalk 的**形状是对的**：一个共享客户端、一个模块化单体、PostgreSQL 做唯一事实源、实时语音和异步分析各自独立进程。
不需要换形状。接下来的问题不在"拆不拆"，而在三件事：

1. **正确性靠每个模块各自手写防线来保证**，同一套防线被抄了很多遍，新增功能的成本越来越高。
2. **能证明的范围停在仓库边界**：自动化很强，但真实语音、真实登录、真实设备都没有闭环，"未验证"清单比功能清单长得快。
3. **产品真正的资产——学习数据——还没有为长期使用设计**：只有当前状态，没有历史，周报和趋势类功能因此做不下去。

规划围绕这三件事展开。

## 2. 不变的原则

这些是已经做对、以后也不该动的决定。任何一轮工作如果要违反其中一条，应当先停下来改这份文档。

| 原则                    | 含义                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------- |
| 一个业务客户端          | Web、iOS、macOS 共用 `apps/vite-app`；平台差异只进 `src/platform/`，不为某一端写 UI |
| 模块化单体              | 业务事务留在一个 FastAPI 服务内；Agent 与分析 Worker 是独立进程，不是独立服务       |
| PostgreSQL 是唯一事实源 | 不引入第二个存储来保存业务状态；缓存、队列都用 PG 或进程内结构                      |
| 失败时关闭              | 认证、凭据、通话占用、合成结果都宁可拒绝也不静默降级                                |
| 契约先于实现            | 跨进程、跨端的行为先写契约文档和类型，再写代码                                      |
| 证据分级                | "代码存在""自动化通过""真实环境验证"是三种不同状态，文档和汇报里不混用              |

## 3. 目标结构

### 3.1 前端：从"组件各管各的"到四层

现状是组件直接调 API、自己管请求代际、自己订阅认证和前后台。`ActiveSessions`、`DailyProgress`、
`WeeklyProgress`、`WeeklyGrammar` 四处各有一套几乎相同的防线，`store/conversation.ts` 同时承担导航、
启动编排和会话状态。目标是让依赖只朝一个方向流动：

```text
app        应用外壳：认证门、导航、主题                      （薄）
features   按页面划分：dashboard / session / review / doc-chat / settings
data       远程数据访问：带认证代际与前后台门禁的查询和变更     （新增的一层）
core       lib/api（生成类型）、lib/auth、store 中的纯状态机、i18n
platform   平台能力接口与各端实现
```

关键是新增的 **data 层**。它把"发起时绑定账号与 revision、后台或离线不请求、迟到响应丢弃、认证变化后清空重查、
分页与去重"收成一个通用机制，组件只声明"我要什么数据"。这一层做成之后：

- 四个数据区块各自缩到以渲染为主，新增区块不再需要重新发明防线；
- 防线本身只在一处测试，现有那些 4000 行级别的组件测试可以逐步收敛；
- 导航（在哪个页面）与会话状态机（通话处于什么阶段）可以分开，Router 的问题届时自然有答案。

是否引入现成的服务端状态库（如 TanStack Query）是这一层的实现选择，不是目标本身。现有的认证代际语义
比通用库的默认行为严格，无论自研还是封装，都必须先把现有语义写成这一层的契约测试。**这是需要决策的一点**（见 §6）。

层与层之间的依赖方向应当由 lint 规则强制，而不是靠约定。

### 3.2 契约：让 OpenAPI 成为唯一的接口事实

后端已经导出 `openapi.json` 并生成 TypeScript 类型，但只用了一半：`lib/api.ts` 里还有十来个手写接口，
E2E 用的 Fake API 是 800 多行手写代码，本次评审发现它缺主路径上的两个接口，就是因为没有任何机制保证它与真实接口一致。

目标是三处都从同一份契约派生：

```text
backend 路由  ──导出──▶  openapi.json  ──生成──▶  前端类型（全部，不留手写）
                              │
                              └──校验──▶  Fake API 的每个响应、以及它缺少的路由
```

同样的思路延伸到另外两类目前没有机器可读契约的接口：Agent 通过 DataChannel 发给客户端的消息（现在只有
`agent_error`，以后会有更多），以及分析 Job 的错误码。它们应当有各自的 schema，由前后端共同引用。

做到这一步，"接口变了但某一端不知道"这一类问题就从评审能发现变成 CI 必然发现。

### 3.3 后端：单体内部按领域收拢

后端的顶层结构适合当前体量，不需要重排目录。要做的是让 `routers/` 真正变薄，把散在路由里的规则收进三个领域：

| 领域       | 负责                                                   | 现在的问题                                                    |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| 会话与通话 | 会话生命周期、幂等、活动发现、Token、调度、单端占用    | 准入规则（套餐、密钥验证）在 token 与 dispatch 路由里各写一遍 |
| 学习       | 分析 Job、发音与语法评估、知识追踪、课程推荐、周度聚合 | 评估来源是 demo 规则加可选 mock，真实 Provider 的接入点不清晰 |
| 身份与设置 | 认证、用户映射、BYOK 凭据、主题                        | 基本到位                                                      |

其中最值得提前设计的是**学习领域的评估接口**：把"发音评估""语法检测"定义成可替换的提供方，每个提供方声明
自己的来源、模型版本、是否合成、置信度（这些字段已经存在于数据模型中）。这样真实发音评估、LLM 语法纠错
（TODO 中的 SGEC）接入时是新增一个实现，而不是改分析流程；合成与真实结果的隔离规则也只在一处执行。

可观测性属于这里：分析队列积压、延迟、失败率，以及 Agent 的启动与错误，应当有统一的结构化事件，
哪怕第一步只是写日志并在健康检查里暴露几个计数。

### 3.4 学习数据：补上时间维度

这是我认为长期最重要、目前最薄弱的一块。现在的 `knowledge_states` 只保存每个技能的**当前**掌握度，
没有历史；`TODO.md` 里"掌握度环比""发音趋势""练习时长""下周重点"几项都卡在"没有历史数据"或"口径未定"上。
继续逐项补统计接口会越补越难，因为缺的是底层。

目标是增加一张只追加的**学习事件**记录，作为所有趋势类功能的来源：

```text
会话结束 ──▶ 分析 Job ──▶ 学习事件（只追加）
                              │   技能、观察结果、来源、是否合成、所属会话、发生时间
                              ├──▶ 当前知识状态（现有表，改为可由事件重算）
                              ├──▶ 周度/月度快照（按需物化）
                              └──▶ 周报、趋势、下周重点（只读事件与快照）
```

要点：

- 事件是事实，状态和报表都是派生。算法版本调整后可以在不改写旧事件的前提下做版本化只读重算。
- 合成结果照样记录但带标记，派生时统一排除，延续现有"合成不进真实掌握度"的规则。
- "练习时长"这类口径问题变成"从哪些事件怎么算"的定义问题，可以先存数据、后定口径。
- 这张表从建立那天起才有数据，**越晚建，能回看的历史越短**。所以它的优先级高于任何具体的周报指标。

用户已于 2026-11-12 确认 B1 的数据生命周期政策：

- 切换时以 `source=legacy_unknown` 的时点基线承接旧掌握度，明确旧历史趋势不可恢复；旧
  `pending` 和按现有规则可重试的 `failed` Job 走新事务，成功旧 Job 不回填，业务时间取真实
  `sessions.ended_at`，BKT 按 `apply_seq`。
- 账户存续期保留事件明细，不设固定 TTL，也不做快照裁剪。唯一首批业务删除例外是本平台整账号
  注销：硬删事件、转录、分析、评估和派生状态，不匿名化保留副本，不操作外部 IdP，不增加单会话
  删除；备份和法定/特殊保留的生产方案另定。
- 本人可导出包含事件、知识状态、已有转录和评估的结构化 JSON，保留来源、合成标记和版本，排除
  密钥、内部提示词和 Provider 完整原始响应。
- 本版不开放成功后的重新分析；失败重试和只读重算保留。现有四参数冻结为 `bkt-v1`，新版本不得
  改写旧事件。

设计政策已经确认，但源码、ORM、迁移、DDL、切换工具、导出和删除 API 尚未实施；生产切换、真实
数据、备份策略及会话音频切片采集都不在本批范围。

### 3.5 平台：能力接口，按证据推进

`src/platform/` 现在有探测、地址解析和生命周期三块，认证完全是浏览器实现。目标是让平台层暴露一组**能力**，
业务代码只问"能不能、怎么做"，不问"是什么平台"：

| 能力       | Web 实现               | 原生实现的前提                     |
| ---------- | ---------------------- | ---------------------------------- |
| 生命周期   | 已有                   | iOS 已有；macOS 待 CP-03 设备证据  |
| 认证会话   | 整页重定向（已有）     | 系统认证会话与回跳，待 CP-03/CP-04 |
| 安全存储   | sessionStorage（已有） | Keychain，待 CP-04                 |
| 麦克风权限 | 隐式（由 SDK 触发）    | 预检与被拒引导，待设备证据         |
| 文件选择   | `<input type=file>`    | 待 CP-05 验证是否需要适配          |

顺序上坚持现有约定：**接口形状由第一个真实的原生实现决定**，不在没有设备证据时预先抽象。
macOS 沿用已规划的路径（正式壳放在 `apps/vite-app/src-tauri/`，构建产物对齐 `dist/<platform>/<mode>` 与 manifest），
是否采用 Tauri 仍以 CP-03 的结论为准。

### 3.6 交付：建立一个能说"验证过"的环境

目前所有"未验证"条目的共同原因是没有一个带真实依赖的环境。这不是某一项功能的缺口，而是整个验证体系缺了一层：

```text
单元与组件测试        ← 已有，强
Fake API 浏览器 E2E   ← 已有，强
契约校验              ← §3.2 补上
无密钥运行时          ← 已有（tools/keyfree-runtime）
预发布环境冒烟        ← 缺：真实 LiveKit、真实 IdP、真实 Provider、HTTPS 入口
设备验收              ← 缺：iOS 真机、macOS
```

建议把"建立预发布环境"当作一个独立的里程碑，而不是散在各功能里等条件：一个带 TLS 的入口、一次性迁移任务、
就绪探针、测试用 IdP 租户与 LiveKit 项目、最小的一组真实链路冒烟（登录 → 开始练习 → 说一句话 → 结束 → 看到分析）。
有了它，`ARCHITECTURE.md` §7 里剩下的风险大半可以关闭或量化，功能也才能从"代码已实现"变成"可以发布"。

这一步需要账号、密钥和费用决策，只能由你发起（见 §6）。

## 4. 路线

四个阶段，前两个可以并行。每个阶段给出的是**退出条件**，具体任务在开工时拆进 `TODO.md`。

| 阶段 | 主题             | 做什么                                                                        | 退出条件                                                                                                                                          |
| ---- | ---------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| A    | 契约与数据层     | §3.2 全部；§3.1 的 data 层与四个数据区块迁移；后端准入规则收拢                | 前端无手写接口类型；Fake API 受契约校验；四个区块不再各自实现请求防线；三测试树计数不降                                                           |
| B    | 学习数据底座     | §3.4 的 B1-1～B1-5：事件表、事务写入、基线重算、JSON 导出与整账号删除         | 每个切换后成功分析 Job 恰有一条完成事件；事件重算的掌握度与当前值一致；合成数据隔离有测试。本轮只做专用合成 PostgreSQL 验证，生产切换另过发布门禁 |
| C    | 真实环境闭环     | §3.6 的预发布环境；真实登录、真实语音、真实分析各一条冒烟；可观测性最小集     | 一条端到端真实链路可重复执行并留有证据；`ARCHITECTURE.md` §7 的 P0 与两条以上 P1 关闭                                                             |
| D    | 原生端与产品扩展 | §3.5 的认证与存储能力接口及原生实现；macOS 正式接入；基于学习事件的周报与趋势 | iOS 真机与 macOS 各完成一次真实登录到分析的闭环；周报指标只读事件与快照                                                                           |

#### B1 实施顺序

五张卡按 B1-1～B1-5 的顺序推进，具体写集与验收见 [`TODO.md`](../TODO.md)。B1-4/B1-5 如新增
HTTP 接口，Fake API 成功响应 fixture、Node 契约测试和 A3 operation 覆盖审计属于同一卡写集；
OpenAPI/TypeScript 更新不能替代这些测试，也不能静默扩大 missing/空 schema 豁免。本批不新增
产品 UI 或真实依赖。

1. **B1-1 模型、新增迁移与约束**：建立 `learning_events` 的 identity、CHECK、唯一约束、外键和索引，
   旧迁移只增不改；退出条件是专用空合成库升级/current 与约束回归通过。
2. **B1-2 同事务事件写入与 BKT 隔离**：成功 Job 的事件、评估、状态和 Job 成功态原子提交；用户锁确保
   同用户顺序，幂等键保证重试不重复；退出条件是并发、交叉来源、全合成和失败回滚测试通过。
3. **B1-3 基线工具与只读校验**：生成幂等 `legacy_unknown` 快照，并在单一 `REPEATABLE READ READ ONLY`
   快照内按 watermark 重算校验；退出条件是切换顺序、并发边界和重算差异的合成库测试通过，不运行
   生产切换。
4. **B1-4 本人数据结构化 JSON 导出**：只导出本人事件、状态、转录和评估，保留来源/合成/版本并排除
   敏感内部数据；若新增 HTTP 导出接口，Fake API 成功响应 fixture、Node 契约测试和 A3 operation
   覆盖审计须同卡完成。退出条件是认证隔离、稳定 schema、敏感字段排除、A3 无新增豁免及生成物门禁
   通过。
5. **B1-5 本平台整账号硬删除**：整账号事务删除全部已确认业务数据，不碰外部 IdP、不增加单会话删除；
   若新增 HTTP 注销接口，Fake API 成功响应 fixture、Node 契约测试和 A3 operation 覆盖审计须同卡
   完成。退出条件是外键顺序、回滚、幂等、跨账号隔离、零业务残留、HTTP 成功契约与 A3 无新增豁免
   通过，备份/特殊保留留给后续方案。

文档随每卡更新，B1-5 后做最终收口。生产切换、真实数据和音频采集另走独立授权与发布门禁。

排序的理由：

- **A 先做**，因为它不依赖任何外部条件，并且降低之后每一步的成本。
- **B 尽早做**，因为历史数据无法补录，晚一个月就少一个月。
- **C 不依赖 A、B**，只依赖外部资源，资源到位就可以开始；它是从"能演示"到"能发布"的分界。
- **D 放最后**，因为原生端的每一项都需要 C 提供的真实登录环境和设备，而周报需要 B 积累的数据。

## 5. 怎么分工给模型

你提到细节可以交给 Sonnet 或 Opus。按这几轮的经验，适合的切法是：

| 工作类型                                     | 适合                       | 交付时要给的东西                                         |
| -------------------------------------------- | -------------------------- | -------------------------------------------------------- |
| 有现成测试兜底的机械重构、类型替换、文案迁移 | Sonnet                     | 范围、"测试文件零改动"或明确的断言变更清单、三测试树计数 |
| 新增一层抽象并迁移多个调用方（如 data 层）   | Opus，或先由更强模型定契约 | 先有契约文档与契约测试，再迁移；每个调用方一轮           |
| 数据模型与迁移（如学习事件表）               | 契约由人确认后再实施       | 表结构、写入点、重算校验方法；迁移单独审查               |
| 真实环境相关                                 | 需要你在场                 | 模型准备脚本与检查清单，执行与凭据由你掌握               |

两条不分模型都适用的规矩：一轮只做一件事；交付必须附实际运行的命令和结果，没跑的写"未运行"。

## 6. 仍需另行决定的事

data 层采用现有代码收敛的方案 A，只读 data 层已随 PR #149 交付，本项不再是待决事项。

1. **是否建立预发布环境，以及何时。** 这决定阶段 C 能否开始，也决定"未验证"清单是继续增长还是开始缩短。
2. **B1 五卡完成后的生产切换窗口。** 设计政策已确认，但当前不切生产、不动真实数据；何时执行需另过发布门禁。
3. **备份、法定/特殊保留及会话音频采集方案。** 这些不在 B1 首版，涉及生产合规与独立隐私决策。
4. **macOS 是否继续走 Tauri。** 由 CP-03 设备证据决定，本文不预设。

## 7. 明确不做

- 不拆微服务，不为三端各建应用，不抽 `shared-core` 包。
- 不引入第二个数据存储或消息队列。
- 不在没有设备证据时设计原生接口。
- 不为了"整洁"做全量目录搬迁；目录跟着 §3.1 的分层在迁移时顺带归位。
- 不把自动化通过写成真实环境验证通过。
