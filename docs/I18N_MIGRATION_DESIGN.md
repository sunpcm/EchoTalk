## 现状与边界

前端文案集中在 `apps/vite-app/src/i18n/zh-CN.ts` 的单语言 TypeScript 对象，若干模块直接导入
`zhCN`；10 个真实技能的中文 label 位于同一文件，`apps/vite-app/src/i18n/skillLabels.ts` 只负责
已知 key 的既有回退。当前前端没有 i18n 运行时依赖。

文案已经使用 `{status}`、`{count}`、`{date}` 等单花括号占位符，部分调用点自行拼接或替换。
这与 i18next 默认的双花括号 `{{value}}` 插值语法不兼容，不能把现有对象原样交给默认引擎后就称为
迁移完成。未来批准实施时，必须先盘点全部资源与调用点，再显式转换/映射占位符或采用经过验证的
兼容层；不得自研消息引擎，也不得把普通文本切换为 HTML 渲染。验收必须实际渲染并确认中文文案
无残留模板，同时覆盖 `0`、空值、缺参数与既有转义行为。

Provider 真实名称、技能 label、ARIA 文本以及现有中文和日期行为属于迁移技术前置和既有合同保护。
这些是本次迁移的兼容验收前置；若需改变，应另行更新相关合同，不由本卡路线选择隐式授权。
Provider 元数据继续保持后端 catalog 原值，不因 UI 本地化而被前端重命名。首期只迁移现有 `zh-CN`
文案并保持这些行为兼容；未来新增第二语言译文时，ARIA 等文案应随该语言另外验证，而不是永远
不翻译。

## 语义必须分开

- **母语**：用户自身的语言背景，现有字段为 `user_profiles.native_language`；本卡不改变其语义。
- **目标学习语言**：当前产品学习目标仍是 English，不因 UI locale 改变。
- **UI locale**：首期推荐固定 `zh-CN`，只决定界面文案语言。
- **报告时区**：使用 IANA 时区标识决定日期窗口与报告边界，不能被 locale、浏览器语言或框架默认值
  替代。

框架迁移不能顺手改变已确认的日期窗口、时区或用户设置语义。

## 语言、fallback 与持久化

首期建议只保留 `zh-CN` 并显式设为默认；不新增第二语言资源，不读取浏览器语言自动切换，不根据
学习目标切换 UI，也不新增 locale 存储或界面设置。只有在未来引入第二语言前，才单独确认
localStorage、账号级 `ui_locale` 或本地覆盖等持久化方案。

缺失 key 可回退到 `zh-CN`；参数缺失或类型不符应在开发期失败，运行时使用安全文案，不向用户展示
原始模板。fallback、框架依赖、语言范围和持久化是彼此独立的批准门。

## 未来实施与验收

1. 先批准框架、依赖、版本、包体、运行时与初始化层，并固定 key/formatter API。
2. 只接入 `zh-CN` 最小初始化，完成一个模块试点；旧中文文案、ARIA、技能 label、Provider 元数据
   与日期行为逐项对照。
3. 按模块渐进替换直接 `zhCN` 访问，持续验证资源覆盖、插值转换、复数边界、日期时区和缺失 key
   回退；任何键或参数错误都不能透出原始模板。
4. 只有引入第二语言时才另卡落地语言设置和持久化；不把该工作混入首期框架迁移。

未来验收至少需要现有中文与 ARIA 的语义对照、所有资源的实际渲染回归、Chromium/WebKit 关键路径、
宽窄屏与键盘/读屏检查。以上是未来门槛。实施节点未运行测试、服务、数据库或真实外部依赖；主控

## 已固定的技术前置与合同保护

- 母语、目标学习语言、UI locale 与 IANA 报告时区保持四个独立维度。
- Provider 真实名称继续使用后端 catalog 原值，不在前端翻译改写。
- 首期迁移必须保持现有中文、技能 label、ARIA 和日期行为兼容；第二语言译文未来随该语言另行验收。
- 单花括号资源必须显式转换/映射，并在实际渲染中回归 `0`、空值、缺参数、转义及无残留模板。
