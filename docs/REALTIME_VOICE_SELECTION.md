# 实时语音栈选型与升级决策

> 核验日期：2026-11-22。适用基线：`codex/docs-single-source-20261121@79a605db8572de0ed60890e839bc985e9e143759`。
> 本文保存选型依据、候选路线和验收口径；功能、进度、卡点与开单只查根目录 [`TODO.md`](../TODO.md)。
> 当前产品与 iOS 开发暂停。本文不启动升级、评测、迁移或外部服务调用。

## 1. 结论与适用范围

当前适合作为**保留并验证的候选源码/锁定配置**：客户端经 LiveKit 房间发布音频，Agent 使用
STT → LLM → TTS，结束后由独立 Worker 做持久化分析。基线真实媒体尚未验证，也没有同语料、
同设备、同地域的项目实测，因此不声称现有 cascade、原生语音模型、自托管 LiveKit 或 Agora
已分出高低。

后续选择先分为两个问题：

1. **媒体与编排层**：继续 LiveKit 或 Agents、改用 Pipecat 等编排、评估 Agora RTC，还是由客户端
   直连模型。它决定会话建立、断线恢复、多端能力和运维责任。
2. **语音能力层**：继续 STT → LLM → TTS 的级联，或让原生音频模型直接听和说。它决定话轮、
   响应生成以及音频属性如何进入反馈流程；两层并非必须一起更换。

教学判断、持久化、学习入账和隐私政策仍是本产品自己的服务端职责；教学闭环不绑定某个供应商。
采用某个 RTC 或语音模型，不自动改变这些职责，也不自动证明真实语音全链路已通过。

候选路线为：

- **A 当前 cascade**：保留现有 LiveKit + Agents + Silero 的候选结构，先核验已知安全项，再在
  用户授权范围内完成真实媒体验证与独立可归因实验。
- **B LiveKit + 原生语音**：媒体与房间保持 LiveKit，为需要音频属性或更低响应时延的特定场景
  评估原生音频模型；教学规则和结果写入继续由后端控制。
- **C 同能力原生直连**：在 LiveKit 外建立原生模型直连通道。可复用业务鉴权、教学后端和账本，
  但媒体凭据、会话适配、恢复和观测路径要重核或补齐；它与 B 同模型、同条件比较后决定。
- **D 有证据才换 RTC/编排**：目标地域存在可复现的网络或运维收益，并且有迁移证据时，才评估
  Agora、Pipecat 或其他组合；品牌覆盖范围不能替代本项目测试。

本文优先采用 A，B 作为按场景验证的增量；C、D 是备选研究路线。当前没有采用 A 以外的决定。

## 2. 业务需求与三层职责

实时英语陪练需要让学习者自然开口、在适度停顿后得到回应、在被误纠错或抢话时能控制话轮，
结束后得到可解释的反馈。DocTalk 还会加入长上下文；弱网、原生麦克风、权限和断线恢复属于
同一产品体验。技术选型应服务于这些行为，而不是只比较一个模型的演示音质。

| 层次               | 当前职责                                                                                          | 换厂商时仍须存在的约束                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 媒体、鉴权与编排   | API 创建会话、签发 Token、dispatch Agent；客户端挂载 LiveKit Room；Agent 启动语音管线             | 认证主体、会话归属、断线恢复、多端冲突、错误脱敏、录音与保留策略都不能借换栈放宽   |
| 语音理解与表达     | STT、LLM、TTS，或原生音频模型的听和说；Silero 提供语音活动边界                                    | 学习者停顿、自我纠正、打断、噪声和中英夹用要按固定语料对测，不能只测清晰短句       |
| 教学评估与学习事实 | 结束事务创建 Analysis Job；Worker 评估并写学习事件；SGEC 使用受信身份；BKT 仅接受符合门禁的新观察 | 转录、模型回复、厂商回调或客户端自述都不是自动可信的评估结果、发音分数或掌握度事实 |

LiveKit 或 Agora 提供实时连接；Deepgram、Cartesia、OpenAI Realtime 等提供部分语音能力；
PostgreSQL 中本产品的会话、评估和学习事件才是学习进度事实。任一语音厂商都不能替代最后
这一层。

“实时转录”和“可持续学习账本”也不是同一件事。当前原生音频能力若能产出文本，可以用于对话，
但专业发音评分仍应使用能核验声学证据的服务；任何原生模型事件若成为学习观察，仍须经过本产品
的受信来源、课程技能映射、覆盖校验和事务约束。参见
[`ARCHITECTURE.md`](./ARCHITECTURE.md) 与 [`B2_LEDGER_CONTRACT.md`](./B2_LEDGER_CONTRACT.md)。

Worker 分析、Provider 限额与计费、iOS 原生音频和真实部署。配置齐全、Token 成功、Fake API
通过、API 健康均不能代替有声媒体验收。现有录音、报告上传和保留配置必须实核；未传 `record`
不能作为“不录音”的证据。`CALL_LEASE_MODE=livekit_cloud` 是 Cloud 占用模式，不能与“已部署
真实 Cloud”或普通 Cloud 媒体连接混为一谈。

还需要纠正以下断言：

- “所有主流口语 App 都在用 LiveKit”没有证据。Speak 有明确生产平台证据；Praktika、Duolingo、
  ELSA、Talkpal、HelloTalk 的公开材料披露范围与工作负载不同，不能拼成同一家厂商的统一答案。
- Speak 的公开生产架构文章明确描述 LiveKit Cloud 与 Agents 支撑其语音平台，也有较完整的多地区、
  cascade/原生语音和评测实践。它是高价值工程对照，不能写成 LiveKit 只被 Speak 用来做短期 demo，
  也不能把它的规模、指标或成本直接移植给本项目。
- “纯原生语音一定不能教学”过强。原生模型负责听说，后端仍可负责课程状态、工具调用、评估和
  持久化；需要验证的是可靠性、成本、音频证据可用性及供应商边界。
- “绑定原生语音厂商就必须交出全部教学数据”同样过强。必须逐项核验音频、转录、日志和回调
  流向、保留期与凭据责任，不能假定任意数据都归同一厂商。
- ChatGPT 描述过自建 Pion relay/transceiver 的超大规模路径，这只提供无需每个会话占用独立
  公网 UDP 端口的架构案例；不能推导所有同类产品都应自建，也不能据此判断其所有时期是否使用
  LiveKit。

同类技术评估继续沿用 `TODO.md` 现有 `OPS-T4` 与 `#30` 入口，真实语音闭环验收使用
`VOICE-T1`；本页不另立总账或新开单。

## 6. 平台与语音模型的互补关系

LiveKit 提供连接、房间、参与者事件、Agent dispatch 和媒体路由；它也可通过插件或原生模型接入
语音能力。把“RTC”和“语音生成方式”分开，才能在不重建客户端与鉴权的前提下做局部实验。
当前 LiveKit 的官方模型文档同时描述级联组合和原生音频模型；这证明其能力范围，不证明本树已
启用某个原生语音功能。

| 可选层                        | 可解决的问题                              | 迁移代价与主要风险                                                                  | 何时值得验证                                                       |
| ----------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| LiveKit Cloud 媒体            | 现成信令、NAT 穿越、媒体路由与地区入口    | 供应商、数据流向、套餐和地域限制须逐项纳入成本/隐私决策                             | 需要较少自营媒体运维，且网络与合规条件可接受                       |
| LiveKit 自托管                | 自己控制服务端部署与网络边界              | 计算、UDP 入口、监控、升级、故障恢复和扩容转为自有责任；开源与托管功能存在差异      | 网络、数据或部署约束证明自托管的持续收益                           |
| 客户端同厂商直连              | 特定原生音频 API 的较短集成路径           | 重核媒体凭据、会话适配、重连、设备生命周期、观测和失败 UX；可复用业务鉴权与教学后端 | 特定模型或简化链路有可测收益，且能补齐媒体与安全边界               |
| Pipecat + LiveKit Transport   | 保留 LiveKit 媒体、尝试另一套 Agent 编排  | 重写编排接口、事件映射和测试；若同时换 Daily 或其他传输，迁移范围更大               | 有可归因问题表明 Agents 编排是阻碍，而非话轮或 Provider 问题       |
| Agora RTC / Conversational AI | 另一套 RTC 与网络覆盖，或已使用其会话能力 | 房间模型、鉴权、Agent 启动、错误和恢复全要重接；套餐与工作负载分别核验              | 目标地域确有可复现连接收益，且教学闭环迁移有完整方案               |
| 原生语音模型（不同接入方式）  | 直接处理音频属性、缩短生成链路的候选      | 话轮设置、工具与教学约束、可观测性、输出一致性、成本和供应商数据边界都须对测        | 某场景明确需要音色、韵律或低响应时延，且细粒度教学判断可保留在后端 |

当前在线 Turn Detector 文档说明可配置本地模型和云端模型，也允许自托管部署显式选择云端 `v1`；
使用 Cloud 凭据与按套餐/开发额度计费，不能写成“自托管只能用本地模型”。但这些在线能力
**不会自动变成已 pin SDK 的运行时行为**。后续实验必须按目标 SDK 核对导入路径、插件换代、
模型依赖、与 STT 自带端点检测的冲突及计费，不能用当前文档替代安装包验证。

## 7. 场景与候选设计

| 候选                | 结构                                                     | 主要收益                                           | 新增负担                                                       | 最低验证范围                                              |
| ------------------- | -------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------- |
| A：现有 cascade     | LiveKit + Agents + Deepgram/LLM/Cartesia；持续调整话轮   | 文本可检查、供应商可替换、已有候选源码链路         | 多段时延相加；音频属性可能在转写中丢失；默认模型不透明         | 先核安全项；固定语料基线；分别核话轮、STT、TTS、LLM       |
| B：LiveKit + native | 同一媒体与鉴权；特定场景由原生模型听说，教学评估仍在后端 | 可探索需音频属性的场景，减少整条级联；保留既有房间 | 新增供应商生命周期、事件和价格；部分场景可能无需更换主对话路径 | 与 A 同语料对测，证明教学判断、话轮、成本与隐私可接受     |
| C：同 native 直连   | 原生模型由客户端或独立连接直接交互；复用业务后端和账本   | 可简化实时链路、针对一个模型优化，教学闭环可保留   | 媒体凭据、会话适配、恢复、多端和观测要重核或补齐               | 与 B 同模型、同条件比较简捷性、网络、费用、教学与安全证据 |
| D：替换 RTC/编排    | 保持能力目标，改变 Agora/Pipecat 等组合                  | 可能解决地域网络或特定编排问题                     | 客户端、服务端、部署和运维大范围迁移；证据常来自其他工作负载   | 先证明 A/B 下的问题来自该层；再做单变量、回退明确的试点   |

不做自动迁移。候选 B 也可以在 LiveKit 的 Agent 接入范围内验证多种音频模型，而不必马上改
客户端。候选 C 可在业务鉴权、教学后端和账本不变的前提下，补齐客户端媒体接入与会话适配；
它与 B 的取舍在相同模型、语料、设备、网络和费用口径下决定。候选 D 不因某竞品采用而入选，
也不因品牌覆盖广而入选。

专业发音反馈和对话中即时纠错分开考虑：前者需要声学证据与独立评分契约，后者可依据当场对话或
课程规则给提示。即使原生模型能判断“说得像不像”，也不能跳过发音分数字段、来源、置信度、
错误映射和课程数据版本的校验。发音关闭时，不应阻断独立的语法路径，也不应将模拟分写进真实
掌握度。

## 8. 固定语料与可归因实验

### 8.1 固定输入与运行条件

验收恢复后，以 `#30` 的 30–50 轮英语学习脚本为起点，保留原始音频和逐轮参考文本。至少覆盖
流畅短答、0.5–2.0 秒句中停顿、填充词与自我纠正、TTS 播放时打断、慢速 A2/B1、噪声、长
DocTalk 上下文。录音留存与主体授权另按隐私约定；无授权时只保存可在测试环境使用的合成或专用
语料，不能把真实用户音频留在未经批准的新设施。

| 运行条件   | 要固定的变量                                                                 |
| ---------- | ---------------------------------------------------------------------------- |
| 身份与房间 | 同一专用测试账号、相同 Room/租约模式和设备组合                               |
| 网络       | 至少目标地域近端、远端及弱网一组；记录测速、丢包、时区与时间                 |
| 设备       | 同一浏览器或同一版本 iOS、相同录放条件；耳机与麦克风差异单列                 |
| 模型       | 实际 resolved 模型、voice、采样率、端点设置、Provider 区域；禁止“默认即固定” |
| 上下文     | 相同 DocTalk 正文、轮数、系统提示和课程目录版本                              |
| 成本记录   | 测试当天定价快照、媒体/Agent/模型/评估/存储及重试计价口径                    |

每个候选版本单独建立配置快照。Agent SDK、插件及其必需的 OpenAI SDK 依赖作为兼容包族一并
评估和升级；前端 RTC、实际模型与话轮配置按层对测，必要时一次只变一层，以定位差异。包族内部
不机械拆成各自独立的升级单元；临时候选不能直接成为生产 pin。

### 8.2 记录的指标

- 话轮结束到最终 STT、首个 LLM token、首个可听助手音频的时间；同时记录 p50、p95，不用
  厂商首字节或网页展示数字替代“用户何时听见”。
- 抢话/误端点、漏打断、自我纠正后的分句与合并、转录修正、WER、目标音素可辨识度、音质主观
  评分、教学准确性和 CEFR 适配。
- 每轮与每 10 分钟的总成本，包含平台媒体、Agent 计算、STT/LLM/TTS 或原生音频、评估、
  录音观察、存储、重试和可能的跨地域流量；BYOK 仍需承担供应商与平台费用。
- 失败率、超时、断线重连、快速结束再开、原生音频会话恢复，以及 BYOK 错误是否保留原配置
  并安全失败。

评测输出至少保存配置、语料版本、机器/设备、网络、实际模型、日期、统计对象和原始汇总。
可归因结果应可复跑；录音、密钥与个人数据不进 Git。

### 8.3 准入、停止和回滚

`#30` 的可选主指标仍然适用：**p50 从用户说完到首个可听音频至少改善 15%**，或对犹豫学习者
显著减少误端点，或在相近延迟/成本下明确改善 STT/TTS，或修复具体的兼容性和可靠性缺陷。
它只是可选准入，不是必须达到的承诺。

无论是否有 15% 改善，任何路线都要先排除不可接受退化：

- p95 尾延迟不得在目标地域、弱网或高负载中恶化到显著伤害交互；尾延迟、失败率和超时率
  必须在固定场景上比较，不能用均值掩盖尾部。
- 误纠错、误切句、漏打断和教学偏离不得恶化；主观音质和发音可辨识度不能因“更快”而降低。
- 数据流向、录音/上传、保留和删除须符合当前获准政策；未知状态不能当作“没有风险”。
- BYOK 的自定义轨失败必须按现有契约明确报错，不得静默回退系统 Key 或产生不明费用。
- 原有鉴权、会话、分析、SGEC 和学习事件门禁必须保持；新语音事件不能绕过账本资格判断。

额外的绝对值门限（如具体 p95 毫秒、误纠错率、准确率、成本上限）当前**待产品与教学裁定**，
不能由本文凭空设定。没有获准的阈值就保留原始数据并标为无法作最终采用结论。网络、成本、
隐私或质量存在不可接受的未知时，停止扩大试点并保持本轮已验证的安全配置。

回滚对象必须是**本轮实测通过的安全配置**，包括实际核验的兼容包族、客户端、Provider 模型/
区域配置、话轮设置与测试证据；不能把当前候选配置当作已经验证的生产路径，也绝不把回滚目标
写成历史上的 `1.4.3`。源声明中的 `livekit-agents` 1.6.10 达到所引插件 Key 日志泄露公告的
修复线，但不代表所有安全问题已闭环；历史日志泄露与轮换仍须按实际部署核验。新增录音和音频
切片不能因回滚而被默认永久保存；删除数据库卷也不能作为回滚手段。

## 9. 成本、地域、隐私与供应商边界

当前没有本项目可用的总价排名，也不写固定每分钟价格。比较应在相同语料、相同时长和相同地域
下记录实际计费。媒体连接、Agent 托管、原生音频/STT/LLM/TTS、上下文长度、评估、录音和失败
重试都可能分别产生费用；自托管会有机器、网络、值班和升级等变动成本，不是固定或免费替代。
BYOK 只是把模型费用的承担者与密钥归属分开，并非免费，也不能保证 RTC 或后端调用不经第三方。

地域决策按真实用户所在网络而不是供应商宣传覆盖来定。至少区分新加坡或目标用户的近端路径、
中国大陆可达性、跨境出口与团队运维所在地。Cloud、自托管和不同模型端点有不同入口与数据
存储位置；`language_hint`、Flux 或其他新参数的端点/插件兼容性必须实核。OpenAI Realtime
有 WebRTC 指南、Gemini 有原生音频 API、Qwen 有按区域分布的实时接口、豆包提供原生语音候选；
这些能力描述并不代表它们在本项目有相同延迟、英文教学质量或费用。

涉及录音或音频切片时，先定用途、最短必要保留期、访问人、导出/删除路径和跨境流向，再决定
上传到哪里。`REAL_FLOW_ACCEPTANCE.md` 的真实语音前置明确要求核对 recording、报告上传和保留，
本文不授权新的采集。评估服务只接收必要的已授权输入，临时缓存、观测日志、失败重试和 RTT
记录同样属于数据边界。

BYOK 的边界还包括：

- 自定义模型失败时停止或提示用户修正，不能未经同意切换系统 Key。
- 供应商的新端点不默认覆写现有自定义配置、模型名、voice 或区域。
- 服务端长期 Key 不打包或持久化到客户端；现有 BYOK 设置输入仍按既有受控验证保存。直连优先
  使用短时媒体凭据，使服务端 Key 不暴露给客户端。
- 凭据不写入测试记录、评测日志或公开文档；轮换与撤销按既有安全流程验证。
- 选择原生模型时，明确其是否处理原始音频、文本、上下文或工具参数，以及各自保留多久。

## 10. 实施、版本快照与后续入口

当前用户可授权既有链路进行真实媒体验证，但产品开发仍暂停。已知安全缺陷必须在真实接入
Provider Key 前处理；这些修复不表示安全问题已全部闭环。B/C/D 涉及代码变更的方案，须在
用户恢复相应实施范围后推进，不借本次验收扩大产品开发授权。

推荐顺序如下：

1. 记录候选源码/锁定配置的实际解析结果；先核已声明的安全修复、日志泄露与 Key 轮换边界。
2. 经用户授权完成 A 的真实媒体、固定语料与录音/数据检查；未通过前不把 A 当已验收路径。
3. 在授权范围内处理剩余可归因的安全与兼容问题；兼容包族与前端、模型、话轮配置分层验证。
4. 针对具体教学痛点评估 B，并与 C 在同模型、同条件下比较简捷性、网络、费用和教学边界。
5. 仅当 A/B 的问题指向媒体或编排层，并有多地域网络、运维或可靠性的可复现证据，才试 D。
6. 每次采用后保留独立回退点；没有合格证据就保持本轮已验证的安全配置。

版本在每次设计或实施前重新核验，不能从本文直接复制升级。尤其要重新阅读目标 LiveKit
[Agents 版本与模型文档](https://docs.livekit.io/agents/models/)、
[话轮检测文档](https://docs.livekit.io/agents/logic/turns/turn-detector/)、
[自托管说明](https://docs.livekit.io/transport/self-hosting/) 和目标客户端发行说明，并核对本仓
实际锁文件及插件是否透传所需参数。`#198` 中的 Agent/client/components 版本、`v1-mini`
与 `livekit-local-inference` 约束只作为历史候选；实施时按目标 SDK 重核路径、依赖和端点。

本文不维护新的进度表。执行真实交互、升级和 Turn Detector/language_hint 评估，继续使用
`TODO.md` 中现有 `VOICE-T1`、`OPS-T4` 和 `#30` 入口；若已有入口不再适合记录决定，再由用户
按现有总账规则裁定，避免出现另一套状态来源。
