## 1. 目标与边界

B2 为后续成功的分析结果建立只追加的学习事件链，并在同一事务内更新当前知识状态。开发期从
`p_init=.1` 开始，旧测试数据与旧 Job 可丢弃；必要的课程和技能种子、来源表及既有结构保留。
不建 `legacy_unknown` 知识状态基线，不承接旧测试 Job，不回填历史。正式用户的 retention、删除与
导出政策在上线前另定。

本轮确认可实施的范围限于代码、迁移文件及能在现有边界内完成的离线检查。迁移文件写入不代表已应用；
PG 新表验证必须使用经批准的具体测试环境和执行权限，不能以 `create_all` 或 skip 绕过。实施完成前
工作包保持未勾选，不能记为 B2 已完成。

## 3. 工作包

每包从当前已评审的 `main` 和本轮决策文档重新建立变更范围，逐包 Review；不采用“从旧候选 cherry-pick
后一次评审”的方式。现有功能若已提供所需片段，应先做差异、契约和测试比较，再决定复用；不能以旧
候选的报告、测试计数或“全部通过”代替当前树的证据。

### P0：契约冻结与候选差异审计

从当前 `main`、`docs/LEARNING_EVENTS_DESIGN.md` 和 `docs/NEXT_PHASE_DECISIONS.md` 形成事件字段、来源关系、
合成门控、幂等键、用户锁顺序、`bkt-v1` 语义及重算快照契约。逐项审计旧候选的模型、迁移、写入服务、
重放服务和测试；列出直接可复用、需适配、应丢弃的片段。清理已确认属于旧基线切换的设计，保留未来
真实用户切换的备选项，避免把清理脚本和正式 retention 一并引入。

验收：字段与事件类型的正负例明确；干净起步与正式政策边界无歧义；候选差异审计能定位每个待迁移
文件的当前 `main` 对应契约；不修改数据库或运行迁移。P0 通过独立评审仍不替代后续实现验收。
本包纳入实施修改或测试时，须按 §4 跑三树；纯只读审计未跑某树时写明原因并将该树门禁保持未通过。

### P1：表结构与迁移文件、离线检查

新增事件模型、单条线性 Alembic 迁移及结构契约测试。只保留开发期需要的基线类型和约束设计，
是否保留 cutover 控制表应由 P0 契约决定；旧知识状态基线不是本轮必需入口。迁移文件只准备，不执行；
不把迁移写成自动清库、自动回填或部署触发器。

离线检查至少覆盖 ORM 与迁移的 revision 关系、字段形状、CHECK、外键、部分唯一索引、状态转换约束和
降级脚本的静态审查；同时按 §4 跑三树。本包可以完成获准的离线代码与迁移文件准备，但 PG 表检查、
约束反向测试、空库 `upgrade`/`current` 和 downgrade/re-upgrade 必须另经专用数据库执行放行。
数据库门禁未运行时只能记为“离线准备完成、P1 完整验收/合 main 未通过”，不能写为完整通过。

### P2：同事务事件写入与真实源 BKT

在成功 Job 的同一事务写完评估来源行、完成事件、规范化观察、当前 `knowledge_states` 和 Job 成功状态；
锁定用户行覆盖首次创建状态；事件和来源必须属于同一用户、Session、Job。只对非合成、技能有效的
新观察按确定性顺序调用冻结的 `bkt-v1`，失败或取消整体回滚。完成事件包含各评估方向的 coverage；
未配置、已评估零错误和评估失败须分开记录。全合成数据写完成事件，但不创建或更新 BKT 状态。

只读契约中的幂等键在同一 Job 的 restart/stale recovery/失败重试中复用，不含 `attempt_count`。已存在事件
必须完整核对归属、来源、载荷和批次；半批、冲突或无法证明完整提交时 fail closed，不能重放部分 BKT。
不实现本阶段未开放的重新分析身份。

旧候选中的旧基线切换、账号删除、导出 API、readiness 等相邻实现不自动进入本包。真实 Provider 接入、
正式删除/导出政策和 Job 并发调度策略也不属于本包。代码修改包须按 §4 跑三树；数据库写入、并发和
用户锁验证未获放行时，只能交付可审代码与离线结果，P2 完整验收和合 main 门禁保持未通过。

### P3：只读一致快照重算校验

首条数据查询前固定
`BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY`，绑定当前
`MAX(apply_seq)` 为 watermark；事件、成功 Job、来源关系和 `knowledge_states` 都只读同一快照。
开发期从 `p_init=.1` 重放新事件；若未来选择时点基线，再按另行确认的基线语义引入。校验幂等键与
来源归属一致、成功 Job 有完整事件、观察顺序与算法版本符合 `bkt-v1`，并按建议的 `abs(diff) <= 1e-9`
比较派生状态。校验只报告问题，不修生产或测试业务数据。

发布前至少用可重复的合成事件集、并发写入边界和可回滚的专用数据库副本验证；实际业务库、正式用户
数据和未获准的测试环境不进入本轮。代码修改后须按 §4 跑三树；无法在获批快照/环境中运行时，数据库
重算与变异门禁保持未通过，本包不得标为完整验收或合 main。

## 4. 公共验收与首失败处理

每个代码修改或测试工作包都必须运行 **Vite Vitest、Playwright E2E 和 backend pytest 三树**，并另跑
适用的 Ruff、后端格式、schema/类型检查。测试零改动不等于免跑三树；没有执行某树时，必须写明具体
原因、把该包门禁保持未通过，不能以局部 pytest、旧候选结果或“测试无关”代替。数据库迁移、新表 PG
集成与数据库变异按 §3 另设放行门禁；未放行时可完成离线代码准备，但不得标该包完整验收或合 main，
也不得用旧基线三树全绿代替新表验证。

契约至少包含以下负例，并与对应正向用例成对：

- 跨用户、跨 Session、跨 Job 的事件或来源组合被拒绝，且无事件、无 BKT 写集。
- 相同幂等键但载荷、合成标记或来源不同时 fail closed；同一 Job 重试不重复累计观察。
- 只插入一部分完成事件/观察时不能提交伪成功；全合成或无有效 mapped 技能时不更新状态。
- 用户并发写入下事件顺序、状态更新与 Job 成功保持一个事务边界；不以全局 sequence 或随机时间代替用户内顺序。
- 重算在一致性快照中的 watermark 固定后，不把快照后提交误判为异常；算法参数或版本不符时报告问题。

每个关键门禁安排有效变异测试，变异应使对应断言真实失败，再逐字节恢复源码并复验。删除关键负例后
仍全绿、只得到拒绝退出码或没有有效失败摘要，都不能记作变异被杀死。首次失败保留原始日志、命令与
真实退出码；修复使用新证据编号，不回写旧结果。

## 6. 依赖与已知风险

- 旧候选混有其他产品能力，直接整支合并会扩大产品与权限范围；应沿用 P0 的逐契约重审。
- 只有 `SKIP LOCKED` 的 Job 锁不能代替用户内串行，遗漏用户锁会导致首次创建状态竞争。
- 把重新分析伪装成 retry 会破坏事件批次和趋势去重；本阶段保持不开放。
- 自然周快照、正式 retention 和真实发音数据尚需后续设计；环比的确认口径不能证明指标已可上线。
- 正式环境的资源费用尚未批准，设备、真实 Provider、LiveKit、IdP 和服务验收阻断保持开放。
